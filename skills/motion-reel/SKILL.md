# Motion Reel

서비스 홍보용 또는 사내 소개용 모션 그래픽 영상을 리서치부터 최종 MP4까지 만든다. 결과물은 1920×1080, 60fps, H.264, 오디오 포함 MP4이다.

이 스킬이 쓰는 방식: 영상의 모든 프레임을 시간 `t`의 순수 함수로 그리는 HTML 파일을 만들고, `scripts/render.mjs`가 헤드리스 Chrome에서 `t`를 1/60초씩 옮기며 캡처해 ffmpeg로 인코딩한다. 실시간 재생에 의존하지 않으므로 복잡한 장면도 프레임이 빠지지 않고, 같은 입력은 같은 영상을 만든다.

## 결과물 위치

작업 디렉터리 아래 `reels/<서비스-슬러그>/`에 모은다.

```
reels/<slug>/
├── brief.md         요청 해석(대상, 청중, 톤), 리서치 결과와 출처
├── storyboard.md    샷 목록(박자, 화면, 문구, 기법, 소리)
├── index.html       장면 파일 (브라우저로 열면 실시간 미리보기)
├── cues.json        소리 큐 (index.html 에서 추출)
├── audio.wav        합성한 음악과 효과음
├── stills/          검수용 정지 프레임
├── contact.png      검수용 밀착 인화(0.5초 간격 프레임 모음)
└── reel.mp4         최종 영상
```

## 준비

```bash
SKILL=<이 SKILL.md 가 있는 디렉터리>
[ -d "$SKILL/scripts/node_modules/playwright-core" ] || npm install --prefix "$SKILL/scripts"
which ffmpeg python3 node
```
Chrome 이 설치되어 있으면 그것을 쓴다. 없으면 `npx playwright-core install chromium`을 실행하거나 `CHROME_PATH`로 실행 파일을 지정한다. ffmpeg 가 없으면 사용자에게 설치(`brew install ffmpeg`)를 요청하고 멈춘다.

## 작업 순서

### 0. 요청 해석

리서치 전에 네 가지를 정해 brief.md 상단에 적는다.

업계 규칙(안전 영역, 읽기 속도, 깜빡임, 소리 크기, 인코딩)과 그 근거는 `references/conventions.md`에 있다. 이 단계에서 읽는다. 이 문서의 수치 규칙은 그 문서에서 왔다.

**길이.** 사용자가 길이를 정하지 않으면 30초로 만든다. 15초는 사용자가 요청할 때만 쓴다. 30초는 기능과 사용 예를 읽힐 만큼 보여 줄 수 있는 길이이고, 15초는 이름과 핵심 한 가지만 남는 길이이다.

**대상 종류.**
- 외부 서비스: 공개된 회사 서비스나 제품. 1단계의 웹 리서치를 따른다.
- 사용자 자신의 프로젝트: "내가 만든", "우리 팀이 만든", 저장소 경로, 사내 도구 이름이 나오는 경우. 1단계의 저장소 리서치를 따른다. 저장소 경로를 알 수 없으면 사용자에게 경로를 묻는다. 웹에 없는 대상을 웹에서 찾으며 시간을 쓰지 않는다.

**청중.** 외부 고객인지, 회사 동료(개발자, 기획자, 경영진)인지. 사내 동료가 청중이면 판매 문구보다 "무엇을 해결하고, 어떻게 쓰고, 어디서 시작하는가"가 중요하다.

**톤.** 아래 표에서 고른다. 사용자가 "강렬하게", "트레일러처럼", "하이프"처럼 강도를 명시하지 않으면 `보통`을 쓴다. "역동적인"은 화면 움직임이 많다는 뜻으로 읽고, 강한 비트나 흔들림을 요구하는 것으로 읽지 않는다. 사내 소개와 기술 소개는 `차분` 또는 `보통`을 쓴다.

| 톤 | BPM | 박 수 (15초 / 30초) | 샷 수 (15초 / 30초) | 카메라 흔들림, 플래시, 글리치, 색수차 | 음악 `energy` | 진입 곡선 |
|---|---|---|---|---|---|---|
| 차분 | 96 | 24 / 48 | 4~5 / 7~9 | 쓰지 않는다 | `low` | `E.outCubic`, `E.inOutCubic` |
| 보통 | 112 | 28 / 56 | 5~6 / 9~11 | 결말에 1회 이하 | `mid` | `E.outExpo`, `E.snap` |
| 강렬 | 128 | 32 / 64 | 7~9 / 12~15 | 전환마다 쓸 수 있다 | `high` | `E.snap`, `E.outBack`, 스프링 |

어느 톤에서도 플래시, 글리치, 밝기 반전은 어떤 1초 구간에서든 3회 이하로 쓴다(WCAG 2.3.1. 근거와 면적 예외는 conventions.md 4절).

톤이 낮을수록 움직임 수를 줄이고, 줄인 만큼 한 요소의 움직임을 정확하게 만든다. 차분한 톤에서도 선형 이동과 단순 페이드는 쓰지 않는다. 박 길이가 달라져도 2단계 구성표의 비율(훅 12%, 전환 19%, 본론 38%, 증거 12%, 결말 19%)을 그대로 적용한다.

### 1. 리서치 → brief.md

홍보 영상의 문구는 짧아서 틀린 사실 하나가 영상 전체의 신뢰를 잃게 한다. 공식 출처를 우선한다. WebSearch, 웹 페이지 읽기 도구(없으면 web-fetch 에이전트)로 다음을 모은다.

- 서비스 이름의 정확한 표기(대소문자, 띄어쓰기, 한글/영문 병기)
- 공식 한 줄 소개와 태그라인
- 대상 사용자와 해결하는 문제
- 핵심 기능 3개(공식 사이트의 표현 기준)
- 증거 수치: 사용자 수, 고객사 수, 성능, 수상 등. 수치마다 출처 URL과 기준 시점을 적는다. 출처가 없는 수치는 영상에 넣지 않는다.
- 브랜드 시각 요소: 주 색상(공식 브랜드 가이드나 공식 사이트 CSS의 hex), 글꼴 인상(기하학적 산세리프, 세리프, 고정폭 등), 제품 화면의 구성
- 행동 유도 문구와 URL

리서치는 검색 10회 안팎, 약 5분 안에 끝낸다. 30초 영상에 들어가는 사실은 이름, 기능 3개와 각각의 사용 예, 수치 1~2개, 태그라인이 전부이다. 이것이 확보되면 더 찾지 않는다.

출처를 열지 못했을 때의 처리:
- 웹 페이지 읽기 도구가 CSS를 주지 않으면 `curl -sL <공식 사이트> | grep -oE '#[0-9a-fA-F]{6}' | sort | uniq -c | sort -rn | head`로 색상 빈도를 본다.
- 크기 제한이나 403으로 1차 출처(공시 문서, 보도자료)를 열지 못하면 `curl -sL -A "Mozilla/5.0" <URL> | grep -o '<찾는 문구>.\{0,200\}'`로 필요한 부분만 확인한다. 그래도 실패하면 같은 수치를 적은 2차 출처 2곳 이상이 일치할 때만 쓰고, brief 에 `2차 출처`로 표시한다.
- 검색 결과 요약문만 본 수치는 쓰지 않는다.

사용자 요청이 모호하면(동명의 서비스가 여럿 등) 가장 가능성 높은 대상을 고르고 brief 첫 줄에 그 판단을 적는다. 사용자가 로고 파일을 주지 않았으면 로고 이미지를 웹에서 가져오지 않고, 로고 도형을 SVG나 CSS로 다시 그리지도 않는다. 로고는 형태 그대로 쓰여야 하는 상표이고, 다시 그린 로고는 공식 로고와 미세하게 달라 오히려 품질을 떨어뜨린다. 서비스 이름을 브랜드 인상에 맞는 글꼴로 조판한 워드마크로 대신한다. 로고의 색과 기본 도형(원, 사각형 등)을 장면의 모티프로 쓰는 것은 허용한다. 전달할 때 워드마크로 대신했다는 사실을 알린다.

**사용자 자신의 프로젝트일 때.** 웹 대신 저장소를 읽는다. README, docs, 예제 디렉터리, 공개 API(진입 모듈의 export), 테스트, 벤치마크 결과, `git log`(기여자 수, 첫 커밋 시점)에서 다음을 모은다.
- 프로젝트 이름의 정확한 표기와 한 줄 설명(README 첫 문단 기준)
- 이 프로젝트가 없을 때의 문제: README의 동기 절, 커밋 본문, 이슈에 적힌 것
- 핵심 개념이나 기능 3개
- 대표 사용 코드 1개: 예제나 README에서 그대로 가져온 3~8줄. 영상에서 코드를 보일 때 이것만 쓴다. 존재하지 않는 API를 지어내지 않는다.
- 수치: 벤치마크, 코드 줄 수 감소, 적용 프로젝트 수 등. 저장소의 파일이나 사용자의 말에 근거가 있는 것만 쓴다. 근거 파일 경로를 출처로 적는다.
- 시작 방법: 설치 명령, 저장소 경로, 문서 위치, 문의 채널. 결말 장면의 CTA가 된다.
- 시각 요소: 프로젝트에 로고나 색이 정해져 있으면 그것을 쓰고, 없으면 회사 브랜드 색이나 중립 팔레트를 쓴다.

정보가 부족하면(동기나 시작 방법이 저장소에 없으면) 지어내지 말고 사용자에게 한 번에 모아 묻는다.

brief.md 형식:
```markdown
# <대상> 브리프
길이 / 대상 종류 / 청중 / 톤: ...
대상 판단: (모호했을 때만)
한 줄 소개: ...
대상 사용자 / 문제: ...
핵심 기능: 1) ... 2) ... 3) ...
증거 수치: | 수치 | 의미 | 출처 | 기준 시점 |
브랜드: 색상 #..., #...; 글꼴 인상 ...; 제품 화면 특징 ...
CTA: ...
출처 목록: ...
```

### 2. 콘셉트와 스토리보드 → storyboard.md

**콘셉트 한 문장.** 대상(서비스, 프레임워크)이 사용자에게 하는 핵심 동작 하나를 시각 언어로 정한다. 예: 결제 서비스 → "점 하나가 이동하며 모든 장면을 잇는다", 협업 도구 → "카드가 모여 하나의 화면이 된다", AI 서비스 → "무작위 문자가 의미 있는 문장으로 해독된다". 영상 전체가 이 시각 규칙 하나를 공유한다. 장면마다 다른 기법을 늘어놓으면 기술 데모처럼 보이고 서비스가 기억되지 않는다.

**모션 언어.** 다음을 정해 storyboard 상단에 적는다.
- 팔레트: 배경, 전경, 강조 1색(브랜드 주 색), 보조 0~2색. 브랜드 자체가 다색(로고 색이 4개 이상)이면 브랜드 색 전체를 쓰되, 한 화면에서 면적이 큰 색은 1~2개로 제한하고 나머지는 작은 요소에만 쓴다.
- 글꼴: 제목용 1개, 본문/라벨용 1개. 한글이 들어가면 한글 글리프가 있는 글꼴(Pretendard, Noto Sans KR, SUIT 등)을 반드시 포함한다.
- 곡선: 진입은 톤 표의 진입 곡선을 쓰고, 퇴장은 같은 계열의 in 곡선(`E.inCubic`, `E.inExpo`)으로 진입보다 짧게 둔다. 선형 이동과 단순 페이드는 쓰지 않는다. 들어온 뒤 멈춰 있는 시간과 움직이는 시간의 대비가 영상의 속도감을 만든다.
- 전환 규칙: 앞 장면의 요소가 다음 장면의 요소가 되는 연결 전환을 최소 2회 넣는다.

**구성.** 모든 컷과 주요 동작은 박 위에 둔다. 역할별 길이는 영상 길이에 대한 비율로 정한다. 시각은 아래 표를 쓰고, 박 번호는 `시각 ÷ (60 / BPM)`을 가장 가까운 정수로 반올림해 정한다.

| 역할 | 비율 | 15초 | 30초 | 내용 |
|---|---|---|---|---|
| 훅 | 12% | 0.0–1.9 | 0.0–3.8 | 첫 프레임부터 움직인다. 문제를 찌르는 짧은 문구나 시각 사건 |
| 전환 | 19% | 1.9–4.7 | 3.8–9.4 | 문제에서 대상으로. 이름 첫 등장 |
| 본론 | 38% | 4.7–10.3 | 9.4–20.6 | 핵심 기능 3개. 15초는 기능당 약 1.9초, 30초는 기능당 약 3.7초로 기능마다 사용 예나 UI 동작까지 보인다 |
| 증거 | 12% | 10.3–12.2 | 20.6–24.4 | 수치 1~2개. 직전 1박은 비트를 빼고 라이저를 둔다 |
| 결말 | 19% | 12.2–15.0 | 24.4–30.0 | 워드마크 + 태그라인 + CTA. 15초는 2.5초 이상, 30초는 4초 이상 두고, 마지막 1.5초는 정지한다 |

다른 길이도 같은 비율로 계산한다.

사내 프레임워크 소개는 역할을 다음처럼 바꾼다: 훅 = 지금 겪는 문제(반복 코드, 느린 작업 등), 전환 = 프로젝트 이름, 본론 = 대표 사용 코드가 타이핑되고 그 결과가 화면에 생기는 장면 + 핵심 개념, 증거 = 저장소 근거가 있는 수치(없으면 생략하고 본론을 늘린다), 결말 = 이름 + 한 줄 설명 + 시작 방법(설치 명령이나 저장소 경로).

**수치 장면의 시간 배분.** 카운트업 중의 숫자는 읽히지 않는다. 카운트업은 0.6초 안에 끝내고(`E.outExpo`), 최종값이 정지한 상태로 최소 1.0초 둔다. 4박 안에 수치 2개를 넣으면 이 조건을 맞출 수 없으므로, 두 번째 수치는 첫 번째와 동시에 진입하게 하거나 1개만 쓴다. 출처 각주는 본문보다 작게(24px 이상) 같은 화면 하단에 둔다.

**읽기 시간.** 사람이 읽어야 하는 문구는 화면에 완전히 보인 상태로 다음 시간 이상 머문다: 한국어 `0.5초 + 음절 수 ÷ 12`, 영어 `0.5초 + 글자 수 ÷ 20`, 어느 경우든 최소 0.84초. 초당 12자와 20자는 Netflix 자막 기준의 성인 읽기 속도이다. 진입 애니메이션 시간은 머무는 시간에 넣지 않는다. 한 줄은 한국어 16자, 영어 42자 이내로 쓴다. 영상 전체 문구는 15초 영상에서 한국어 60음절(영어 30단어), 30초 영상에서 한국어 110음절(영어 55단어) 이내로 쓴다. 문구 언어는 사용자 요청의 언어를 따르고, 서비스 이름과 고유 기능명은 공식 표기를 쓴다.

**샷 목록.** storyboard.md 에 표로 쓴다. 코드를 쓰기 전에 이 표가 완성되어야 장면 사이 연결과 박자가 맞는다.

```markdown
| # | 박 | 화면 | 문구 | 기법 | 다음 샷으로의 전환 | 소리 큐 |
| 1 | 0–6 | 검은 화면에 커서 깜박임, 문장 타이핑 | "회의록, 아직 손으로?" (8음절, 머무는 시간 1.2초 필요) | 타이핑, 마스크 리빌 | 커서가 점으로 줄어 다음 샷의 버튼이 됨 | blip@0.2, type@0.4 |
```

기법은 `references/techniques.md`에서 고른다. 톤 표에서 금지한 효과는 쓰지 않는다. 강렬 톤에서는 영상 전체에 다음을 최소 하나씩 포함하고, 보통과 차분 톤에서는 이 중 3~4개를 고른다: 키네틱 타이포그래피, 마스크 기반 전환, 제품 UI 재현 또는 데이터 시각화, 3D 깊이(CSS 3D 또는 WebGL), 입자 또는 생성형 그래픽, 카메라 움직임(줌 펀치, 흔들림, 패럴랙스). 기법 수보다 연결과 박자가 품질을 정한다.

### 3. 장면 구현 → index.html

```bash
mkdir -p reels/<slug> && cp "$SKILL/assets/template.html" reels/<slug>/index.html
```

템플릿은 엔진(시간 함수, 곡선, 장면 관리, 소리 큐, 그레인, 카메라, 미리보기)과 예시 장면 2개로 되어 있다. 예시 장면은 지우고 스토리보드대로 새로 짠다. 템플릿 상단의 엔진 주석을 먼저 읽는다.

지켜야 할 규칙과 이유:
- 모든 시각 상태를 `update(lt, st)`에서 `lt`만으로 계산한다. CSS `transition`/`animation`, `setTimeout`, `Date.now()`, 시드 없는 `Math.random()`, 이전 프레임 상태 누적을 쓰지 않는다. 렌더러는 임의의 `t`로 건너뛰며 하위 프레임을 찍으므로, 이런 것은 프레임마다 다른 결과나 깨진 프레임을 만든다.
- 장면 구간을 0.1~0.5초 겹쳐 정의하면 전환 중 두 장면이 함께 그려진다. `z`로 쌓임 순서를 정한다.
- 소리 큐는 화면 사건과 같은 시각 상수로 `cue(t, type, opts)`를 호출해 정의한다. 컷마다 whoosh 나 impact, 기능 등장마다 blip/tick, 증거 직전 riser, 결말에 boom 을 둔다. 차분 톤에서는 impact, boom, glitch 대신 blip, tick, whoosh 를 쓴다. 큐 종류: impact, boom, riser, downlifter, whoosh, swoosh_rev, blip, tick, glitch, type, kick. 옵션은 `scripts/sfx.py` 상단 주석에 있다.
- `DURATION`, `music.energy`, BPM은 0단계에서 정한 길이와 톤을 따른다. `music.sections`(템플릿 작업 구역)는 구성표의 비율로 계산된 기본값이다. 스토리보드에서 구간을 바꿨으면 함께 고친다. 카메라 흔들림과 줌 펀치는 작업 구역의 `IMPACTS`, `PUNCHES` 배열에 시각을 넣어 정한다.
- 글꼴은 `<link>`로 불러온다. 렌더러가 `document.fonts.ready`를 기다린다. 캔버스에 글자를 그리는 장면은 `ready` 이후에 build 한다.
- 글자와 로고는 그래픽 안전 영역(상하좌우 5%, 가로 96px, 세로 54px) 안에 둔다. 중요한 움직임은 동작 안전 영역(3.5%, 가로 67px, 세로 38px) 안에 둔다(EBU R 95). 배경, 입자, 전환 막대는 화면 끝까지 써도 된다.
- 읽어야 하는 글자는 24px 이상으로 쓴다. 1080p 화면 글자 최소 크기에는 표준이 없고, 자료마다 22~48px로 다르다(conventions.md). 24px는 이 스킬이 정한 값이다.
- 요소 배치는 `.abs`(기준점 왼쪽 위 0,0) + `set({x, y})`로 한다. `right`/`bottom`으로 붙이는 요소에는 `.abs`를 쓰지 않는다. `set()`은 transform 전체를 덮어쓰므로, 고정 변환이 필요하면 `pre`/`post` 옵션에 넣는다(예: 3D 플립 뒷면 `post: 'rotateY(180deg)'`).
- 외부 이미지를 쓰지 않는다. 아이콘과 도형은 인라인 SVG나 CSS로 그린다. 사용자가 준 로고·이미지 파일은 `reels/<slug>/`에 복사해 상대 경로로 쓴다.

브라우저 미리보기: `open reels/<slug>/index.html` (스페이스 정지, ←/→ 0.1초 이동, `?t=3.2`로 특정 시각 고정). 사용자가 직접 확인하고 싶어할 때 안내한다.

### 4. 정지 프레임 검수

전체 렌더 전에 정지 프레임으로 확인한다. 전체 렌더는 수 분이 걸리고 정지 프레임은 수 초이다.

```bash
cd reels/<slug>
node "$SKILL/scripts/render.mjs" --html index.html --stills <시각 목록, 쉼표 구분> --outdir stills
```

시각은 각 샷의 중간과 각 전환의 한가운데로 고른다. 30초 영상이면 15~20개이다. 이미지 읽기 도구로 모든 정지 프레임을 직접 본다. 확인 항목:
- 문구가 잘리거나 겹치거나 화면 밖으로 나가지 않는가. 의도하지 않은 줄바꿈이 없는가.
- 한글이 대체 글꼴(굴림체 같은 모양)로 그려지지 않았는가.
- 배경 대비 문구가 읽히는가.
- 빈 화면이나 아무것도 없는 프레임이 없는가.
- 서비스 이름 표기와 수치가 brief.md 와 일치하는가.
- 콘셉트 문장의 시각 규칙이 프레임에서 보이는가.

1920px 이미지를 한 장씩 읽으면 토큰이 많이 든다. 2×2로 묶어 한 번에 본다(시각 순서대로 묶인다):
```bash
ffmpeg -v error -y -pattern_type glob -i 'stills/t*.png' -vf "scale=960:-1,tile=2x2:padding=6" stills/sheet_%02d.png
```
문구가 작은 장면이나 의심 가는 프레임만 원본 크기로 다시 본다.

명령이 종료 코드 3으로 끝나면 페이지 JavaScript 오류가 있다는 뜻이다. 출력된 오류를 고친다. 문제를 고치고 같은 시각을 다시 찍어 확인한다. 이 단계를 최소 1회 반복한다.

### 5. 소리와 전체 렌더

```bash
node "$SKILL/scripts/render.mjs" --html index.html --dump-cues cues.json
python3 "$SKILL/scripts/sfx.py" cues.json -o audio.wav
node "$SKILL/scripts/render.mjs" --html index.html --out reel.mp4 --audio audio.wav --blur 2
```

`--blur 2`는 출력 프레임마다 하위 프레임 2개를 평균해 모션 블러를 만든다. 렌더러는 브라우저 4개로 프레임을 나눠 캡처하고(`--workers`), 압축 속도 우선 PNG로 무손실 캡처한다.

렌더 시간 측정값(Apple Silicon Mac, Chrome, 1920×1080 60fps, `--blur 2`, informative-slides 예시 15초 버전):

| 설정 | 시간 |
|---|---|
| 이전 렌더러(Playwright PNG, 순차) | 568초 |
| CDP PNG, 브라우저 1개 | 119초 |
| CDP PNG, 브라우저 4개 (기본값) | 55초 |
| CDP JPEG q95, 브라우저 4개 (`--format jpeg`) | 39초 |

같은 예시의 30초 버전은 기본값으로 88초 걸렸다. 브라우저를 6개, 8개로 늘리면 57초, 59초로 오히려 느려졌다. JPEG 캡처는 PNG 결과와 비교해 PSNR 46.0 dB, SSIM 0.981이었다. 최종 렌더는 PNG로 하고, JPEG는 미리보기에 쓴다. PSNR과 SSIM은 원본과 비교한 화질 지표로, 값이 높을수록 원본에 가깝다.

전체 렌더 명령은 처음부터 백그라운드 실행(Bash 도구의 `run_in_background`)으로 시작하고 완료 알림을 기다린다. 포그라운드로 실행하면 도구가 수 분 뒤 중간에 백그라운드로 옮겨 종료 코드와 출력을 확인하기 어려워진다. 진행 상황은 1초 분량마다 한 줄씩 출력된다. 종료 코드 0과 마지막 줄의 `reel.mp4 (...)`로 완료를 확인한다. 빠른 확인이 필요하면 `--fast --blur 1`(JPEG 캡처, x264 veryfast)로 렌더한다. 프레임레이트는 미리보기와 최종 렌더 모두 60fps로 둔다. `--fps`로 바꾸지 않는다.

### 6. 영상 검수

```bash
# 0.5초 간격, 6열. 행 수 = ceil(길이초 × 2 / 6). 아래는 30초(10행). 15초는 tile=6x5, scale=384
ffmpeg -v error -y -i reel.mp4 -vf "fps=2,scale=320:-1,tile=6x10:padding=4" -frames:v 1 contact.png
ffmpeg -v error -i reel.mp4 -vf blackdetect=d=0.2:pix_th=0.05 -an -f null - 2>&1 | grep black_start
ffprobe -v error -show_entries stream=codec_name,width,height,r_frame_rate,duration -of compact reel.mp4
# 소리 크기: I(평균)가 목표(기본 -16 LUFS) ±1 LU 안인지 확인한다
ffmpeg -nostats -hide_banner -i reel.mp4 -af ebur128=peak=true -f null - 2>&1 | grep -E '^\s+(I|Peak):'
```

렌더러는 오디오를 `--lufs`(기본 -16 LUFS), `--tp`(기본 -1.5 dBTP)로 정규화한다. 방송용이면 `--lufs -23`으로 렌더한다(EBU R 128).

`--blur` 로 렌더한 영상에서는 빠르게 움직이거나 바뀌는 요소(카운트업 숫자 등)가 겹쳐 보인다. 모션 블러에 따른 정상 결과이므로 결함으로 판단하지 않는다. 정지 상태여야 할 프레임에서 겹침이 보일 때만 고친다. contact.png 를 보고 샷 순서와 리듬이 스토리보드와 맞는지, 비슷한 화면이 연속으로 너무 오래 이어지지 않는지 확인한다. 의도하지 않은 검은 구간이 검출되면 고친다. 고친 뒤에는 4~6단계를 다시 수행한다.

### 7. 전달

사용자에게 다음을 짧게 알린다.
- `reel.mp4`의 절대 경로와 사양(해상도, fps, 길이)
- 콘셉트 한 문장과 샷 목록 요약(샷당 한 줄)
- 영상에 쓴 사실과 수치의 출처(brief.md 경로)
- 고른 톤과 그 이유. 더 차분하게 또는 더 강하게 바꾸려면 톤 표의 어느 값을 바꾸는지
- 사용자가 확인해야 할 한계: 로고를 워드마크로 대신했는지, 제품 화면이 재현인지, 음악이 합성음인지
- 수정 방법: 문구나 색을 바꾸려면 index.html 을 고치고 5단계를 다시 실행한다.

## 참고 파일

- `assets/template.html` — 장면 엔진과 예시. 3단계에서 복사한다.
- `references/conventions.md` — 안전 영역, 읽기 속도, 깜빡임, 소리 크기, 인코딩, 움직임 시간의 업계 규칙과 출처, 근거 등급. 0단계에서 읽는다.
- `references/techniques.md` — 타이포, 전환, 형태, 데이터·UI, 공간, 캔버스·WebGL, 후처리 기법과 코드. 2단계에서 기법을 고를 때, 3단계에서 구현할 때 읽는다.
- `scripts/render.mjs` — 정지 프레임, 큐 추출, 영상 렌더.
- `scripts/sfx.py` — 큐로부터 음악과 효과음 합성. 표준 라이브러리만 쓴다.
